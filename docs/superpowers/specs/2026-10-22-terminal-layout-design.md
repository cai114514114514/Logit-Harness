# loh 终端布局与信息层次

这是已批准交互方案的界面修订。用户在 2026-10-22 的实机截图中指出：参考了 Claude Code 未登录的欢迎界面，导致进入对话后仍像欢迎页；对话没有自然靠近底部，蓝色 L 跑到历史中间。用户明确要求“重新构建一个清晰的 CLI”。沿用原 Rust/Ratatui/Crossterm 和已有运行核心，直接在原工作树修改。

## 已确定的体验

- 蓝色 L 是一次进入界面的标识。欢迎页可以紧凑；开始、附着或恢复会话后，不再把大 Logo、版本和工作目录作为不断重绘的活动区头部。它们不得插在工具结果与回复之间，也不因新输出/resize/重连重复写入历史。
- 会话输入栏与简短页脚贴近终端底部。最新活动紧邻输入栏上方，对话和已完成工具结果持续向上进入原生 scrollback。进入会话、完成回复、空闲、工具执行、菜单、切换会话和 resize 都遵守这一规则。
- 当前状态用真实信息说明“正在做什么、持续多久、被什么阻塞”。模型等待/回复流、运行命令、只读查看、工作者、独立验收、暂停收尾、等待工作区拥有者、等待答复或授权必须可区分。
- 输入提示按模式变化：普通对话是继续提问；Plan 是补充只读规划；Engineering 才是补充要求/纠正方向。显示模式不等于仅按最后一条消息猜测，依据当前会话状态。
- 模型回复为主内容；工具默认一行标题/关键路径或命令、状态和简短来源，必要时保留少量结果/失败尾部。长内容显示明确折叠提示，完整内容仍能从详情搜索、展开、复制。
- 原始内部 ID、重复“系统 · 系统”、正常状态转换的英文诊断不占据普通对话的主要位置。详细事件仍保留，不隐藏失败、待答问题、授权、预算耗尽或未知结果等用户必须知道的状态。
- 所有 `/` 命令、literal Skill 参数和来源选择、隐藏密钥设置、后台会话、上下文与 KV 统计保持可用。菜单靠近输入栏，使用可理解的来源/执行时机文字，不把本地操作发给模型。

## 实现者的布局取舍

以上用户意图不要求另造 UI 框架。实现者可按职责拆分启动标识、对话投影、活动摘要、输入/菜单和终端表面，但不建立两套命令分发或两份状态机。

- 启动标识与活动区域分离；普通对话区域不保留三行固定 Logo 槽位。
- 底部区域只容纳当前活动、菜单、输入和页脚；不会为了贴底而把一屏空白塞进每个完成块之间。
- 改变活动区高度时，不能清掉已结算内容或重播它来“移动”历史。需要移动空间时使用受控终端滚动，保持顺序和追加一次约束。
- 原生终端处理自己的 scrollback/reflow；窗口扩大后的既有内容如何回流不作跨终端绝对保证，但输入区位置、无重复历史和可继续输入必须保证。
- 欢迎页、设置表单、会话和临时历史浏览器各有明确布局边界。历史浏览器退出后恢复底部输入，不重建/重播整个会话。
- 保留原始内容与显示摘要的区分。真实长工具流、最终结果、失败/取消和来源信息继续使用已经修复的共享投影；不得为了简化外观丢掉已存内容。

这些是基于现有约束的布局选择，不包含新的插件架构、运行内核、付费实验或额外主题系统。

## 实机验收

使用隔离的真实 macOS PTY 和本地 fixture provider，不触碰用户进程或剪贴板。至少验证：

1. 欢迎 → `hello` → 回复完成 → 多次回复 → 长工具输出，蓝色启动标识只出现一次，完成记录不重放，输入/页脚位置在底部。
2. 在高/矮/宽/窄终端、输入多行中文、打开/关闭 `/` 菜单和历史详情、resize、重连后仍能正确编辑，光标留在输入区域。
3. 对话/Plan/Engineering 三种模式有不同且正确的提示；普通项目只读问答不会伪装成正在执行工程目标。
4. 多工作者、静默命令、模型流、暂停/停止收尾、工作区等待和断线失败都有简明的实际状态；完整原始记录在详情中仍可查询。
5. 普通聊天中的必要错误可见，常规底层诊断不刷屏。检索和复制长工具流保留唯一早期前缀，最终有界结果不覆盖原始流。

检查捕获的彩色 PTY 画面和 scrollback 内容，不能只以测试断言代替视觉检查；它们不是原生 Terminal 窗口截图。完成后重新构建、安装并验证实际 `loh`，更新文档与准确证据。

## 同时存在的功能缺陷

执行核心的 `/diff`、完整历史和 Conversation/Plan resume 修复继续完成。截图中的 `project_instructions` 误拒绝合法绝对根路径也已定位并分配修复。布局实现不重写或绕过这些边界，等待该实现者完成后再进入同一工作树的布局改动。

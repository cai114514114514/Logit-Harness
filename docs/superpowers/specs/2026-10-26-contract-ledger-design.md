# loh 终端：契约账本

2026-10-26。依据设计稿 [2026-10-26-contract-ledger.html](2026-10-26-contract-ledger.html)（第 1 版，基于 97ca1bc）。
用户当天确认了稿中四个待定项，都按建议执行：用“契约 / 条款”命名；浅色终端启动时查询背景色；
条款标签只出现在修改、运行、检查类工具行；为这次重设计开放 IPC，但只能新增。
设计稿里的字符网格就是验收画面。本文补全数据来源、边界和实施默认值，冲突时以本文为准。
[协作优先终端](2026-10-23-terminal-design.md) 和 [团队设计](2026-10-23-team-design.md) 中没有被本文改动的部分继续有效。

## 目的

现在的 loh 看起来像别家 coding agent 的聊天界面：`❯ 你`、`● Logit`，加一串英文工具行。
运行时其实已经有别家没有的东西：条款带版本（`Goal`）、证据绑定版本（`Evidence`），
纠偏是选择性修订，完成前要过独立验收。这些现在只能靠 `/status` 里的计数看到。
这一轮把它们变成界面的主体，让用户一眼看清三件事：要做什么（条款原话）、做到哪了（证据状态）、
这一步为了什么（工具行和状态行上的条款标签）。

## 不变的部分

- 正常终端缓冲区和原生 scrollback：已结算内容只追加一次，活动区和输入贴底。
  沿用 `Surface` 的 committed-output 边界，不重播日志，不用 reverse-index。
- 蓝色 L 只在启动时写一次。成员栏、Ctrl-T、`/agent`、成员视图的控制范围、草稿绑定、
  归档只读，全部保持 10-23 版的行为。
- 工具默认一行；失败、取消、结果未知和来源截断永远可见；Ctrl-O / `/history` 详情不变。
- 状态只说真实发生的事：不估进度百分比，不用“正在理解”遮住阻塞。
- 运行时的完成屏障、调度、权限、模型工具定义、预算和验收规则都不改。界面只呈现运行时已有的判断。

## 名称

界面统一用“契约 / 条款”。契约版本记作 `v{revision}`，条款编号沿用 `Requirement.id`（`r1`、`r2`……）。
`/status` 现有的“需求版本 / 有效需求”字样同步改成“契约 v{n} · {m} 条条款”。
内部类型名（`Goal`、`Requirement`）不改。

## 视觉语言

### 发言竖条

每条发言的每个视觉行都以竖条开头，取代 `❯ 你` / `● Logit` 标题行：

| 竖条 | 发言者 | 颜色 |
|---|---|---|
| `▌` | 你 | ACCENT |
| `│` | 主控（Logit、回答侧问、处理补充） | MUTED |
| `┃` | 成员；主控视图里竖条后紧跟成员名 `┃ 迁移 · …` | MEMBER[n] |
| `║` | 独立验收 | FRESH |

正文保持终端前景色，竖条后空一格。连续多段属于同一发言的，中间的空行不加竖条。
NO_COLOR 下靠竖条粗细和成员名区分发言者。系统通知（`·` 开头的 Note）保持现状。

### 工具行

`│ ✓ 读取  src/storage.rs                    48 行 · 0.1s`

- 发言竖条，状态符号 `✓ ✕ ⋯ ?`，中文动词，两个空格，对象。右侧对齐：结果 · 耗时 · 条款标签。
- 动词：`read_file` 读取、`search_*`/`list_files` 搜索、`apply_patch` 修改、`shell` 运行、
  `check` 检查、`fetch`/浏览器 抓取/浏览，其余保留工具名。
- 结果只写真实可得的值：读取的行数、搜索结果数、补丁的 `+增 −删`（可得时）、退出码；
  `检查` 和 `运行` 只在能从输出末尾确定解析出测试汇总时写 `N 通过`，解析不了就不写。
- 耗时取 `ActionStarted` 到 `ActionFinished` 的事件时间差，小于 60 秒写 `4.1s`，否则写 `1m04s`。
- 条款标签（已确认）：只在修改、运行、检查三类工具上显示；而且只在动作作用范围比全部有效条款
  窄的时候显示（主控未聚焦步骤时作用于全部条款，标出来只是噪音）。读取和搜索永远不标。
- 失败尾部、截断提示和分组规则沿用 10-23 版，尾部行缩进到对象列。

### 契约印章

| 印章 | 含义 | 判定 | 颜色 |
|---|---|---|---|
| `○` | 未取证 | 没有当前的非读取通过证据 | MUTED |
| `●` | 有证据 | 有当前的非读取、非评审通过证据 | FRESH |
| `◉` | 已验收 | 有当前的评审证据（verifier 写入） | FRESH |
| `⊘` | 已过期 | 曾有非读取通过证据，但现在都不再当前 | STALE |
| `⊗` | 未通过 | 最新一条当前的非读取证据失败，或最近一次验收判它未通过且之后没有新的通过证据 | FAIL |

- “当前”使用新的 `Evidence::current_version(goal, steps)`：条款版本、epoch、步骤版本都匹配，
  不比对文件指纹。`current` / `current_at` 改为在它之上再比对文件，判定结果不变。
- 正在为某条款工作：有运行中的动作，它的 scope 包含该条款，而且作用范围比全部有效条款窄。
  显示为编号加 ACCENT、粗体、下划线。印章和下划线各表达一件事，可以同时出现（`⊗ r4` 带下划线 = 失败后正在修）。
- 文件变化导致的过期不实时显示：视图每 2 秒刷新一次，不能每次都去哈希文件。文件指纹留到验收时
  由 verifier 核对，`/contract` 底部写明这一口径。

### 卡片

账本卡片写进 scrollback，上边 `╞══ 标题 ══ 副标题 ═══…`，下边 `╘══ … ═══…`，两条边都铺满可用宽度：

- 契约卡（ACCENT）：条款抽取完成时写一次。列出每条有效条款；r1 右侧标“完整原话”。
  底边：“条款只能引用你的原话 · 模型不能删减 · /contract”。
- 修订卡（STALE）：条款每修订一次写一张。条目：`~` 修改（旧文 → 新文）、`+` 新增、`−` 退役、
  `×` 被取消的动作及其条款和结算状态、`⊘ N 项证据过期`及原因、`= 保留 N 个步骤 … 代码不回滚`。
  底边：“契约 v{a} → v{b} · /contract 查看原话与修订链”。
- 验收回执（通过 FRESH，未通过 FAIL）：每条有效条款一行，印章、编号、条款摘要、引用证据的
  种类和描述；未通过的条款下一行写 verifier 给的原因。统计行：“{p}/{n} 通过 · 证据绑定 v{n}
  条款版本、步骤版本与文件指纹”，或“{p}/{n} 通过 · 有条款未通过时不会标记完成”。
  通过时底边写“完成 · 用时 · tokens · KV”，未通过时写“已把 {k} 条失败原因交回 Logit · 继续修复”。
  回执前一行是验收者的抬头：“║ 验收 · 独立上下文 · 读取 N 个文件 · 重跑 M 组测试 · 用时”，
  数字来自 verifier 自己的工具记录。

旧会话没有新事件时，修订仍显示现在那一行“需求修订 {n} · r2, r4”，不补画卡片。

### 颜色 token

| token | 用途 | 实现 |
|---|---|---|
| ACCENT | 品牌 L、你的竖条、选中、进行中、正在处理的条款 | 深色背景 `Rgb(91,156,255)`；浅色背景见下文 |
| FRESH | `● ◉ ✓`、验收回执 | ANSI 绿 |
| STALE | `⊘`、修订卡 | ANSI 黄 |
| FAIL | `⊗ ✕ ×`、退出码、未通过回执 | ANSI 红 |
| MUTED | 次要信息、主控竖条、页脚 | ANSI DarkGray |
| MEMBER[n] | 成员竖条和名字 | 按成员 id 排序后依次取 ANSI 青、品红，然后循环 |

`NO_COLOR` 存在时所有 token 都不着色，只保留粗体和下划线等修饰。

### 浅色终端（已确认）

启动时、开始读取输入之前，查询一次终端背景色（`OSC 11 ; ?`），超时 150ms。
回复的相对亮度大于 0.5 时，ACCENT 改用 `Rgb(0,92,197)`（白底对比度约 6:1）；没有回复、
解析失败、不是 TTY 或设置了 `NO_COLOR` 时沿用现值。查询只做一次，结果在本进程内不变。
查询期间收到的其他字节交还输入队列，不丢失用户按键。

## 画面结构

活动区从上到下：

1. 团队标识和成员栏（仅团队时，沿用 10-23 版）。
2. 契约栏（仅当前视图有工程目标时）。
3. 仍在输出的回答或工具预览。
4. 状态行：需要你处理的事项优先，其次阻塞，最后是当前动作（沿用现有优先级）。
5. 临时菜单。
6. 输入横线、输入、页脚。

### 契约栏

`契约 v1   ○ r1   ⊗ r2   ● r3                      有证据 1/3 · /contract`

- 右侧计数：有验收结论时写“验收通过 {n}/{n}”或“验收 {p}/{n}”，否则写“有证据 {k}/{n}”，
  k 是 `●` 和 `◉` 的条款数。
- 成员视图收窄为“本成员服务  ⊗ r4   契约 v2 · 全部条款 /contract”，只列当前分配的条款。
- 对话模式、没有有效条款、或归档视图都不显示契约栏。

### 状态行

`⋯ 运行 cargo test storage::tests · 服务 r2 · 已用 12s · 距输出 2s`

- 当前动作用和工具行一样的动词和对象。作用范围比全部条款窄时加“服务 r2 r4”。
- 团队主控视图每个忙碌成员一行，行首是成员名（`迁移 ⋯ 运行 …`），等待写“等待 迁移 修复后重跑 · 已等 8s”。
- 空闲时不显示状态行，空闲状态写进输入横线。阻塞和需要你处理的事项照旧显示，规则不变。

### 输入区

- 只留一条上横线：`╶─ {标签} ─────…╴`。标签：
  - 无会话：“新对话”。
  - 对话模式空闲：“对话 · 等待输入”。
  - 工程执行中：“Engineering · 补充或纠正”；已完成：“Engineering · 已完成”；
    Plan 模式：“Plan · 只读”。
  - 团队主控：“主控 · Engineering · 控制整队”；成员视图：“{成员名} · 仅此成员”；
    归档：“{成员名} · 归档只读”。
- 提示符 `▸` 取代 `❯`。去掉输入下方的横线，页脚紧贴输入。
- 页脚左侧是提示，右侧对齐“模型 · tokens · KV”。工程模式提示里加“/contract 契约”。
  团队主控的 token 写“全队 64.3k”，成员视图写成员名。

### 启动

```
██      Logit- Harness  0.1.0
██      deepseek-flash
██████▀ ~/residual

  说出目标，Logit 会把它记成一份可核对的契约。
  打招呼和提问不会建立契约；执行中随时插话，离开终端也会继续。

╶─ 新对话 ─────────────────────────────────╴
 ▸  输入消息、问题，或需要实现的目标…
 Enter 开始 · / 命令 · /sessions 最近会话 · Ctrl-D 退出
```

没有密钥时，说明下面多一行“尚未配置 API Key · /setup 设置”。

### 窄屏

收起顺序：次要快捷键 → token 数 → 条款编号 → 非当前成员。当前身份、控制范围、失败和输入光标始终保留。

- 60 列：卡片里的长条款从左侧省略（`…SQLite，迁移在单一事务内完成`），保留变化的部分；
  契约栏去掉条款间的空格（`○r1 ○r2`），右侧计数写“证据 0/4”；输入横线只留模式。
- 40 列：契约栏放不下条款编号时只剩版本、印章串和计数（`v2 ○⊘○○   0/4 · /contract`），
  四条以内的条款在 40 列仍放得下编号；模式缩写为 `Eng`。
- 比 40×12 还小时，沿用“loh · 请扩大终端窗口”。

## /contract 契约详情

本地命令，不调用模型。临时全屏，复用历史浏览器的 modal 机制；Esc 返回后不重播历史。

- 标题：“契约 v{n} · {m} 条条款 · 修订 {k} 次”，右侧“Esc 返回”。
- 每条条款：印章、编号、当前版本、全文；下面几行依次是来源（你的完整原话 / 你的原话摘录 /
  你的补充，带时间）、修订（旧版本原文 → 当前版本）、证据（编号、种类、描述、是否当前；
  过期的写原因：条款版本、epoch 或步骤版本）、验收结论、正在进行的动作。
- 已退役的条款列在最后，标“已退役 · v{n}”。
- ↑↓ 选择，Enter 展开选中条款的证据原文（证据产物路径和结果），`/` 搜索，`c` 复制该条款的来源原话。
- 底部：“状态按条款版本、步骤版本和 epoch 判断；文件指纹在验收时核对。”
- 证据编号 `e1`、`e2`……是会话内证据列表的序号，只用于显示；真实 ID（`e-<action>`、
  `review-<uuid>`）在展开内容里保留，可以搜索。
- 没有契约时显示“当前没有契约。说出要完成的目标后，Logit 会把它记成契约。”

## 运行时数据（只增不改）

1. `Evidence::current_version(&self, goal, steps) -> bool`：上文的“当前”判定。
2. 新事件 `EventData::Contract { revision, epoch, source, cause, clauses, changes }`：条款抽取完成时
   写一次（revision 1，`cause = "extract"`），每次 `Revised` 之后紧跟着写一次。字段：
   - `clauses`：全部条款（含已退役）的 id、全文、版本、是否有效、来源原话。
   - `changes`：`updated`（id、旧文、新文）、`added`、`retired`、`cancelled`（动作 id、标题、条款、是否已结算）、
     `stale`（证据 id、描述、原因）、`kept`（步骤 id、描述）。
   - 发出位置：`meta.rs` 的 `extract_requirements`，`steering.rs` 的 refine/replace，
     `questions.rs` 的回答，`team/corrections.rs` 的 refine/clarify。四处共用 `Runner::emit_contract`。
3. 新事件 `EventData::Acceptance { revision, passed, checks, summary }`：`verify.rs` 在决定
   完成或驳回之前发出。`checks` 每项：条款 id、是否通过、引用的证据（id、种类、描述）、原因。
4. `SessionView.contract: Option<ContractView>`（serde default）。在 `From<Session>` 里推导：
   每条有效条款的印章、是否正在处理、证据摘要；最近一次验收结论；契约版本。
   最近一次验收结论存进 `Session.acceptance`（serde default），重连后不用重扫事件。
5. `Activity.requirements: BTreeMap<String, u64>`（serde default），取自 action 的 scope；
   另加 `Activity.focused: bool`，表示作用范围比全部有效条款窄。
6. 持久化契约允许新增变体，`User.turn` 已有可选字段的先例。旧会话没有这些数据时按现在的样子回放。

## 验收

1. 设计稿第 01、1–9 帧逐一按字符网格对照：80×24、110×34、60×18、40×12，深色、浅色、NO_COLOR。
   以实际 PTY 输出为准，不以本文或设计稿的手排网格为准。
2. 印章判定的单元测试覆盖五种状态和组合（失败后正在修、验收驳回后有新通过证据、epoch 推进、
   步骤失效、只有读取证据）。
3. 修订卡内容和运行时实际的选择性修复一致：失效步骤、取消的作业、过期证据都来自同一次修订的真实结果。
4. 实况和重放用同一套规则画卡片；重连、缩放、切换视图都不重复写卡片。
5. 旧会话（没有新事件）可以完整回放，界面和现在一致。
6. 完整回归、fmt、严格 Clippy、release 构建；10-23 版的验收项全部仍然通过。
7. 工程验收、交互验收和真实模型表现分别报告。离线 UI 验证不发起付费调用。

loh契约账本

别的 coding agent 给你看一段聊天。loh 给你看一份契约：你说的每一句要求都记成带版本的条款，每一步工作都标明它在为哪条条款服务，证据过期会被标出来，完成必须拿到独立验收的回执。

这份稿子只描述终端里会出现的样子。下面每个画面都是逐格排出的字符网格，中文按 2 格计，和 loh 用的 unicode-width 规则一致；画面以外的说明文字不属于界面。确认之前不改产品代码。

终端配色

00保留什么，改变什么

原样保留（已确认的规格）

  • 正常终端缓冲区和原生 scrollback：已结算内容只追加一次，输入和页脚贴底。
  • 蓝色 L 只在启动时出现一次。
  • 成员栏、Ctrl-T、/agent、成员视图的控制范围、草稿绑定、归档只读。
  • 工具默认一行；失败、取消、未知结果和截断永远可见；Ctrl-O / /history 详情不变。
  • 状态只说真实发生的事，不估进度百分比，不用“正在理解”遮住阻塞。

这一版改变

  • 契约栏常驻活动区：每条条款一个“印章”，显示证据状态。
  • 契约卡 / 修订卡 / 验收回执写进 scrollback，记录契约是怎么建立、怎么改的，又是凭什么完成的。
  • 发言用左侧竖条区分：你 ▌、主控 │、成员 ┃、验收 ║。去掉 Claude Code 的 ● / ❯。
  • 工具行改成中文动词，右侧对齐结果、耗时和所服务的条款。
  • 输入区只留一条上横线，模式和空闲状态写在横线里。
  • 新增 /contract 详情：原话、修订链、证据。

01同一时刻，现在和以后

两边是同一个任务的同一个时刻：第二次启动重复导入导致测试失败，Logit 正在重跑。左边按 44eeeee 的源码重建（工具结果后缀等细节可能略有出入），右边是新设计。

  • 右边一眼能回答三个问题：要做什么（契约 v1 的三条原话）、做到哪了（契约栏：r3 有证据，r2 刚失败、正在重跑，r1 未取证），这一步为了什么（工具行和状态行的 r2）。
  • 左边的同样信息要靠 /status 才能看到，而且只有“需求版本 1，3 项有效需求”这样的计数。

02画面

1 · 启动

要点

  • 蓝色 L、模型、目录各一行，只在启动时写一次。
  • 一句话说清产品行为：目标会变成契约，闲聊不会。
  • 欢迎态没有贴底，紧跟在 shell 输出后面，这一点和现在一致；进入对话后才贴底。
  • 没有密钥时，这里多一行“尚未配置 API Key · /setup 设置”。
数据：screen.model、workspace、key_present

2 · 普通对话

要点

  • 没有契约栏。问候和知识问答不建立工程目标，也不扫描项目。契约栏出现，就说明真的有了需要验收的目标。
  • 空闲时没有单独的状态行，“对话 · 等待输入”写进输入横线，少占一行。
  • 回答保持终端前景色。主控竖条是暗灰色，让正文本身做主角。
数据：session.mode == Conversation，goal 没有活动条款

3 · 工程执行中

要点

  • 契约卡：目标拆成条款时写一次。r1 永远是你的完整原话，r2、r3 只能是原话里的原句摘录（这是 Goal::extract 已有的约束），所以卡片底部写“模型不能删减”。
  • 工具行：✓/✕/⋯ + 中文动词 + 对象，右侧是结果、耗时、所服务的条款。只读步骤不标条款（它们服务全部条款，标出来只是噪音）。
  • 契约栏：○ r1 未取证，⊗ r2 最新检查失败，● r3 有当前证据。下划线和强调色表示正在为它工作。
  • 状态行说明当前动作服务哪条条款：服务 r2。
数据：goal.requirements、evidence[]（版本 / epoch / 步骤新鲜度）、ActionScoped.requirements、activities。这一帧固定用浅色终端显示，方便对照对比度。

4 · 纠偏与修订卡

要点

  • 你的补充一出现，scrollback 里就打出一张修订卡，把运行时实际做的选择性修复摊开：
    • ~ 修改条款（旧文 → 新文）、+ 新增、− 退役
    • × 已取消的动作，以及它作用于哪条条款、是否已结算
    • ⊘ 过期的证据，以及过期原因
    • = 保留的步骤：代码不回滚
  • “新增条款使旧证据失效”是运行时的真实保守策略：新增条款会推进 epoch，旧证据整体过期。卡片照实写出来，不美化。
  • 契约栏同步变成 v2：r3 变成 ⊘，r2 和 r4 带下划线，表示正在处理。
  • 没有这些细节的旧会话，回放时仍显示现在那一行“需求修订 2 · r2, r4”。
数据：新增事件 Revision，在 steering.rs 和 team/corrections.rs 发出 Revised 之后紧接着发出，内容取自 Impact、graph.invalidate 和被取消的作业

5 · 团队并行（主控视图）

要点

  • 成员栏、Ctrl-T、“主控 / 成员·状态”的写法和 10-23 版完全一致。
  • 成员里程碑用粗竖条 ┃ 加成员名，颜色和成员栏一致。NO_COLOR 下靠竖条粗细和名字区分，不靠颜色。
  • 接手任务时写明服务哪些条款、可写哪些目录，所以“谁在为哪条条款工作”在主控视图就看得见。
  • 契约栏在全队之上：⊗ r4 是 测试 的失败，r2 和 r4 带下划线，因为有成员正在处理它们。
  • 每个成员一条状态行，“等待 迁移”这类阻塞照实显示。
数据：team.members、Assignment（步骤、条款、可写路径）、Mail、bindings

5b · 成员视图

要点

  • 头部仍是“测试 · 仅控制此成员”、团队标题和任务，和现在一致。
  • 契约栏在成员视图里收窄成“本成员服务 ⊗ r4”，全部条款走 /contract。成员不能修改契约，所以这里只读。
  • 在这里输入只发给 测试。输入横线写着“仅此成员”。
数据：当前成员 Assignment.requirements，其余同主控

6 · 验收回执

要点

  • 完成时打出验收回执：每条条款对应哪条证据、证据是什么，以及它绑定了哪一版契约。这正是 loh 不同于“模型说做完了”的地方。
  • 验收者使用双竖条 ║，并有“独立上下文”字样。结论段落也用这条竖条，说明这是验收者的话，不是主控的自述。
  • 回执底边写总用时、token 和 KV，给这次任务一个了结。
  • 契约栏全部变成 ◉（已验收），输入横线写“已完成”。
数据：新增事件 Acceptance，在 verify.rs 判定 Completed 或 withheld 之前发出，内容来自 verifier 的 checks 和引用的 Evidence

7 · 验收未通过

要点

  • 回执改用红色边框，标题写“验收未通过”；未通过的条款直接写出原因。
  • “有条款未通过时不会标记完成”：把运行时的完成屏障写在界面上。
  • 通过的条款保持 ◉：verifier 会为已通过的条款写入评审证据，这是真实状态。
  • Logit 接着修复时，r4 带上下划线，状态行写“服务 r4”。
数据：Acceptance.passed = false，失败原因来自 verifier 的 check.reason

8 · 窄屏

  • 60 列：卡片里的长条款从左侧省略（…SQLite，迁移在单一事务内完成），保留变化的部分；契约栏去掉条款间的空格。
  • 40 列：契约栏只剩版本、印章串和计数（v2 ○⊘○○ 0/4），条款编号要进 /contract 才能看到。
  • 收起的顺序：次要快捷键 → token 数 → 条款编号 → 非当前成员。当前身份、控制范围、失败和输入光标始终保留。
  • 比 40×12 还小时，沿用现在的“loh · 请扩大终端窗口”。

9 · /contract 契约详情

要点

  • 临时全屏，复用历史浏览器的 modal，Esc 返回后不重播历史。
  • 每条条款显示：当前版本、来源（完整原话 / 原话摘录 / 你的补充，带时间）、修订链、所有证据及其是否过期，以及验收结论和正在进行的动作。
  • 选中条款时 c 复制你的原话，Enter 展开证据原文。
  • 底部写清判断口径：状态按条款版本、步骤版本和 epoch 判断，文件指纹在验收时核对。
数据：goal.history（修订链）、Requirement.source、evidence[]、最近一次 Acceptance

03视觉语言

契约印章：只表达证据事实

印章含义判定颜色
○未取证没有当前的非读取类通过证据次级灰
●有证据有绑定当前条款版本、epoch 和步骤版本的通过证据，尚未验收绿
◉已验收有当前的独立评审证据（verifier 写入）绿
⊘已过期曾有通过证据，但条款修订、epoch 推进或步骤失效后已不再当前琥珀
⊗未通过最新的当前证据失败，或最近一次验收判它未通过红
r2正在为它工作有运行中的动作，其 scope 包含该条款强调蓝 + 粗体 + 下划线

相比你选择方向时看到的预览，这里去掉了 ◐“进行中”：一个符号只表达一件事。证据状态用圆形印章，“正在做”用下划线，两者可以同时出现，比如 ⊗ r4 带下划线表示失败后正在修。

活动区从上到下

  1. 团队标识和成员栏（仅团队时）
  2. 契约栏（仅工程目标时）
  3. 仍在输出的回答或工具预览
  4. 状态行：需要你处理的事项优先，其次是阻塞，最后是当前动作
  5. 临时菜单
  6. 输入横线、输入、页脚

04运行时需要补的数据，以及诚实边界

  • 契约状态：SessionView 新增 contract 字段（serde default），在 From<Session> 里复用 Evidence::current_at 的版本、epoch 和步骤判断推导。最近一次验收结论存进会话（serde default），重连后无需重扫事件。
  • 契约卡 / 修订卡：新增事件 Revision。抽取条款时也发一次（revision 1），用来画契约卡。
  • 验收回执：新增事件 Acceptance。
  • 条款标签：Activity 增加它所服务的条款，来源是已有的 ActionScoped。
  • 这些都是只增不改：事件持久化契约允许新增变体，User.turn 已有可选字段的先例。没有这些数据的旧会话按现在的样子回放。
  • 不声称的事：契约栏不实时比对文件哈希，因为视图每 2 秒刷新一次，不能每次都去哈希文件。文件变化造成的过期留到验收时由 verifier 核对，详情页底部写明这一口径。
  • 上一轮规格里“不为视觉改 IPC”的约束，这一轮需要你明确放开。

05待你确认

1. 名称：用“契约 / 条款”吗？备选是“需求 / 要求”，更平实，但不如“契约”能表达“说过的话被记下、要兑现”。我建议用契约。
2. 浅色终端上的强调蓝。我建议启动时（输入读取开始之前）查询一次终端背景色（OSC 11，带超时），浅色背景改用更深的蓝；查询不到就沿用现值。也可以维持现状，不改。
3. 工具行右侧的条款标签（· r2）。我建议只在修改、运行、检查这类动作上显示；也可以完全不显示，只放在状态行。

也可以直接指出任何一帧里哪里不对。确认后，我把它写成规格 2026-10-26-contract-ledger-design.md 和实施计划，再开始改代码。
